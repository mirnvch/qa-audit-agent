> **Перечитай этот абзац два раза.** Это, возможно, самая важная мысль всего Модуля 3. После него ты будешь смотреть на любой QA-проект **двумя слоями**: «что у них стандартное» и «что у них своё». Эта пара вопросов сразу скажет тебе **возраст** и **зрелость** проекта.

## Часть 1. Знакомая ситуация

### Представь две столярные мастерские

Зайди в две **разные** столярные мастерские. Обе делают мебель. Обе работают.

**Мастерская 1 — стандартная.** На полке — то, что продаётся в любом магазине инструментов: молоток, набор отвёрток, дрель, шуруповёрт, ножовка, рулетка. Хорошие инструменты, известных марок. Мастер берёт молоток, отвёртку, размечает рулеткой по линейке, делает мебель. **Работает.**

**Мастерская 2 — профессиональная.** На полке — те же самые молотки, дрели, шуруповёрты. Но рядом — **самодельные приспособления**: упор для пилы, на который сразу выставляется нужный угол. Шаблон, по которому за секунду размечается двенадцать одинаковых отверстий. Универсальный кондуктор, в который вставляется заготовка — и она сразу выходит точной. Десятки таких штук, и **никаких** из них нет в магазине.

### Что отличает эти две мастерские

Внешне — почти ничего. Те же базовые инструменты. Те же материалы. Та же мебель на выходе.

А вот по **скорости** и **качеству** — разница в пять раз. Профессиональная мастерская собирает табуретку за двадцать минут. Стандартная — за полтора часа. И с разницей в **точности**: у профессионала все табуретки одинаковые, миллиметр в миллиметр. У стандартного — каждый раз чуть-чуть «авторская работа».

**Почему?** Потому что профессиональная мастерская **построила свой слой** поверх стандартных инструментов. Эти «штуки на полке» — не «излишек», не «понты», не «всё равно мы могли бы и без них». Это — **накопленный опыт** в физической форме. Когда мастер двенадцать раз размечает одно и то же отверстие, он на тринадцатый делает шаблон. Шаблон экономит ему пятнадцать минут на каждой следующей детали.

### Не каждая мастерская доходит до этой стадии

Многие плотники работают **стандартным набором всю жизнь**. И ничего страшного — они делают мебель, зарабатывают, живут. Просто **медленнее** и **с большей дисперсией** качества.

А некоторые — однажды смотрят на свой рабочий день и говорят: «я уже двенадцатый раз размечаю эти отверстия. Хватит. Сделаю шаблон». Это **момент перехода** из «стандартной» в «профессиональную» мастерскую. Не одномоментный — постепенный. Шаблон, упор, кондуктор. Год спустя — полка приспособлений, и работа идёт **в три раза быстрее**.

### Точно так же с QA-проектами

Зрелая QA-команда — это **профессиональная мастерская**. У неё на «полке» те же базовые инструменты: Playwright, Vitest, Pino, Faker, Fishery, AJV, Lefthook, stealth — всё, что мы прошли в уроках 3.1 и 3.2. Это **стандартный набор**. Без него — никуда.

Но **поверх** этих инструментов у зрелой команды есть **свой слой**. Свои «шаблоны и упоры»:
- **Свой** доступ к окружению — типизированный, без `process.env` повсюду.
- **Свой** базовый Page Object — с автологированием каждого клика.
- **Свой** GraphQL/REST клиент — с retry, headers, единым обработчиком ошибок.
- **Свой** реестр созданных тестовых данных — чтобы БД не засорялась.
- **Свой** механизм обогащения ошибок контекстом — чтобы при падении было видно, **какая** сущность и **где** сломалась.
- **Свой** формат отчёта о падении — чтобы Slack-сообщение «у меня тест упал» не требовало пятнадцати уточняющих вопросов.

Когда ты заходишь в **молодой** QA-проект, ты видишь только базовый набор. `process.env.STAGING_URL` в десяти местах. `console.log` повсюду. Каждый тест делает свой `axios.post(...)` к API. Это **стандартная мастерская**. Работает. Но через год у такой команды — двести тестов и **боль** на каждом релизе.

Зрелая команда **проходит этот же путь**, но не остаётся в нём. Через двести тестов она пишет первый кастомный модуль. Через пятьсот — второй. Через тысячу — пятый. И у неё на «полке» появляется набор внутренних модулей, который **никто другой не сделает за неё**.

### Это и есть тема урока

Шесть кастомных модулей — типичные «приспособления» зрелого QA-проекта. Они не из npm. Они написаны **внутри** команды. Они нигде не описаны в чужих туториалах. И именно они отличают «школьный проект, который случайно вырос» от **production-ready инфраструктуры**, на которой команда живёт три года.

После сегодня ты будешь смотреть на чужой код **двойным взглядом**: видеть стандартный набор (Playwright, Faker, AJV) **и** видеть кастомный слой (`ConfigurationManager`, `AppPage`, `GraphQLClient`). И сможешь сказать про любой проект: «это стандартная мастерская» или «это профессиональная».

## Часть 2. Шесть типичных кастомных модулей

Пройдёмся по каждому. Структура такая: **что делает**, **какую боль решает**, **что было бы без него**, **где живёт в проекте**.

### Модуль 1. `ConfigurationManager` — типизированный доступ к окружению

#### Что делает

Это **singleton** (объект, существующий в проекте **в одном экземпляре**), через который тесты получают **настройки окружения**: какой baseURL, какое имя организации, какие feature-флаги, какой API-ключ. И всё это — **типизированно**: возвращаемые значения имеют точный TypeScript-тип, а не «может быть строкой, может быть undefined».

```typescript
import { configManager } from '../support/config';

const baseUrl = configManager.getBaseUrl();         // string
const orgId = configManager.getOrganizationId();    // string
const env = configManager.getEnvironment();         // 'local' | 'dev' | 'stg'
```

#### Боль, которую решает

Без `ConfigurationManager` каждый тест читает окружение через `process.env`:

```typescript
const baseUrl = process.env.BASE_URL;                       // string | undefined
const orgId = process.env.ORGANIZATION_ID;                  // string | undefined
const env = process.env.ENV as 'local' | 'dev' | 'stg';     // type assertion
```

Возникают **четыре** проблемы:

1. **Тип всегда `string | undefined`** — каждый раз надо проверять, что значение есть. Десять тестов = десять проверок.
2. **Опечатки в именах переменных** — `BASE_URL` vs `BASEURL` vs `base_url`. Опечатался — тест молча получит `undefined` и упадёт где-то в районе третьего шага с непонятной ошибкой.
3. **Нет единого списка переменных** — каждый разработчик добавляет «свои» `process.env.MY_CUSTOM_KEY`, и через год в проекте 40 неизвестных переменных.
4. **`type assertion` лжёт** — `process.env.ENV as 'local' | 'dev'` говорит TypeScript «доверяй мне, это `'local'` или `'dev'`», но в runtime может прийти что угодно. TypeScript теряет контроль.

#### Что становится с `ConfigurationManager`

Внутри модуля **один раз** прописана **схема окружения**:

```typescript
class ConfigurationManager {
  private env: EnvironmentConfig;

  constructor() {
    const envName = process.env.ENV ?? 'local';
    this.env = environments[envName];
    this.validate();
  }

  getBaseUrl(): string {
    return this.env.baseUrl;
  }

  getOrganizationId(): string {
    return this.env.organizationId;
  }

  private validate(): void {
    if (!this.env.baseUrl) {
      throw new Error('Missing baseUrl for environment ' + this.env.name);
    }
  }
}

export const configManager = new ConfigurationManager();
```

Теперь:
- Все переменные **собраны в одном файле** (`environments.ts`).
- Каждая возвращается **с точным типом** — без `| undefined`.
- При старте конструктор делает `validate()` — если какой-то критичной переменной нет, проект падает **сразу**, а не через 20 минут на третьем шаге случайного теста.
- Если разработчик хочет добавить переменную — он **должен** обновить тип `EnvironmentConfig` + добавить геттер. Это **тормозит** хаос.

#### Где живёт в проекте

Папка вроде `config/` или `support/config/`, файлы `environments.ts` (данные) и `configManager.ts` (singleton).

#### Тонкий момент

`ConfigurationManager` — это **classic singleton pattern**. У него есть критики («синглтоны — это глобальное состояние, его трудно мокать в unit-тестах»). Это правда. Но в **тестовом проекте** singleton оправдан: конфигурация **читается один раз** при старте процесса, и далее не меняется. Это редкий случай, когда глобальное состояние — это **не баг**, а корректное решение.

### Модуль 2. `AppPage` / `BasePage` — собственный Page Object с автологированием

#### Что делает

Это **базовый класс** для всех Page Object'ов в проекте. Поверх стандартного Playwright-овского `page` (помнишь из 3.1) он добавляет:

- **Action wrappers** — `click(element)`, `fill(element, value)`, `hover(element)` — которые при каждом вызове **автоматически логируют** действие.
- **Pre-action waits** — перед каждым кликом / филлом ждёт, пока элемент станет видимым.
- **Error context** — если что-то падает, в ошибке указано, **какая страница**, **какой элемент**, **сколько ждали**.

```typescript
class OrdersPage extends AppPage {
  protected pageName = 'OrdersPage';

  async openNewOrderDialog(): Promise<void> {
    await this.click(this.selectors.toolbar.newButton);
    // Автоматически логируется:
    //   🖱️ [OrdersPage] Waiting for "New order button"...
    //   🖱️ [OrdersPage] Clicked "New order button" (42ms)
  }
}
```

#### Боль, которую решает

Без `AppPage` каждый разработчик пишет `await page.locator(...).click()` напрямую. В лучшем случае рядом — `console.log('clicked new order button')`. В худшем — никакого лога.

Когда тест падает в CI:
- Без `AppPage`: видишь стек-трейс «`page.click` timeout 30s», и **не знаешь**, на **каком шаге** упало. Каком клике? Каком ожидании? Может, тест уже на пятом действии — но без логов это **угадывание**.
- Без `AppPage`: каждый разработчик логирует **по-своему**. Кто-то `console.log`, кто-то ничего, кто-то длинными строками. В CI — каша.

#### Что становится с `AppPage`

```typescript
abstract class AppPage {
  constructor(protected page: Page) {}
  protected abstract pageName: string;

  async click(entry: SelectorEntry): Promise<void> {
    this.log.debug(`🖱️ [${this.pageName}] Waiting for "${entry.label}"...`);
    const start = Date.now();
    await this.waitAndScroll(entry);
    await entry.locator.click();
    this.log.info(`🖱️ [${this.pageName}] Clicked "${entry.label}" (${Date.now() - start}ms)`);
  }

  async fill(entry: SelectorEntry, value: string): Promise<void> {
    this.log.debug(`✏️ [${this.pageName}] Waiting for "${entry.label}"...`);
    await this.waitAndScroll(entry);
    await entry.locator.fill(value);
    this.log.info(`✏️ [${this.pageName}] Filled "${entry.label}" with "${value}"`);
  }
}
```

Теперь **каждое** действие в **каждом** Page Object **автоматически** логируется в едином формате. При падении в CI ты видишь:

```
🖱️ [LoginPage] Clicked "Sign in button" (45ms)
✏️ [LoginPage] Filled "Email input" with "qa@example.com"
✏️ [LoginPage] Filled "Password input" with "********"
🖱️ [LoginPage] Clicked "Submit button" (52ms)
🖱️ [OrdersPage] Waiting for "New order button"...
ERROR: Element not visible after 30000ms
```

Сразу понятно: тест упал на странице `OrdersPage`, при попытке кликнуть на `New order button`, **который не появился**. Не нужно угадывать.

#### Где живёт в проекте

Папка `pages/base/` с файлами `appPage.ts`, `basePage.ts`, плюс типы для `SelectorEntry` (метаданные локатора + человекочитаемая метка).

#### Тонкий момент

`AppPage` обычно строится **постепенно**. Команда начинает с одного `click()`, затем добавляет `fill()`, потом `hover()`, потом `waitForElement()`. Через год это — **полный фреймворк** со своей системой селекторов, логированием, обработкой ошибок. Это типично — кастомный слой **эволюционирует**.

### Модуль 3. `GraphQLClient` (фасад) — единая точка для всех API-запросов

#### Что делает

Это **facade pattern**: один объект, через который тесты делают **все** API-запросы. Внутри он умеет:

- Делать запросы к GraphQL endpoint (или REST — фасад универсален).
- Подкладывать **headers** (auth-token, organization-id, content-type).
- Делать **retry** при transient-ошибках (5xx, network timeout).
- Валидировать ответы по **схеме** (через AJV из 3.2).
- Логировать каждый запрос/ответ.

```typescript
const apiClient = await createGraphQLClient(env);

const response = await apiClient.createOrder({ name: 'Acme Logistics' });
const orders = await apiClient.getOrders();
const user = await apiClient.updateUser(userId, { role: 'ADMIN' });
```

#### Боль, которую решает

Без фасада каждый тест дёргает API напрямую:

```typescript
const response = await fetch(`${process.env.API_URL}/graphql`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${token}`,
    'X-Organization-Id': process.env.ORG_ID,
  },
  body: JSON.stringify({
    query: `mutation { createOrder(input: { name: "Acme" }) { id name } }`,
  }),
});
const json = await response.json();
```

В **каждом** API-тесте — **двадцать строк** этой обвязки. Если что-то меняется (auth схема, формат headers, retry-стратегия) — обновлять надо в **сотнях** мест.

#### Что становится с `GraphQLClient`

Вся обвязка — **в одном** классе. Тесты вызывают **типизированные методы**: `createOrder(...)`, `getOrders()`, `deleteOrder(id)`. Что внутри — их не касается.

И когда auth-схема меняется — правишь **один** файл. Сотни тестов продолжают работать.

#### Где живёт в проекте

Папка `support/api/` с файлом `graphqlClient.ts`. Часто рядом — `domains/` (подразбиение по сущностям: `users`, `orders`, и т.д.), `schemaValidator.ts` (валидация ответов).

#### Тонкий момент

В очень больших проектах `GraphQLClient` сам становится **слишком большим** (тысячи строк). Тогда применяется **разбиение на домены** — фасад остаётся, но внутри делегирует в `UsersApi`, `OrdersApi` и т.д. Это **рефакторинг роста**, и он типичен через год-два жизни модуля.

### Модуль 4. `seededAssetRepo` — реестр созданных тестовых данных (safety-net)

#### Что делает

Это **реестр**, в который тест **регистрирует** каждую созданную сущность. Если тест успешно прошёл — он сам удаляет (через `apiClient.deleteX()`). Но если тест **упал** на середине — сущность остаётся **зарегистрированной** в реестре, и **специальный reporter** в конце прогона удаляет её сам.

Это **safety-net** — защитная сеть. На случай, если тест умер так, что до cleanup не дошёл.

```typescript
test('create order', async ({ request }) => {
  const order = await apiClient.createOrder(...);

  seededAssetRepo.register({
    type: 'Order',
    id: order.id,
    deleteFn: (oid) => apiClient.deleteOrder(oid),
  });

  // ... остальной тест ...

  await apiClient.deleteOrder(order.id);
  seededAssetRepo.unregister('Order', order.id);
});
```

Если тест упал **между** `register` и `delete` — reporter в конце прогона позовёт `deleteFn(order.id)` и **удалит** сущность.

#### Боль, которую решает

Без реестра — **БД медленно заполняется мусором**. Через полгода в staging-окружении:

- 50 000 «Test QA: User 1717...».
- 30 000 организаций с именами Faker.
- 100 000 заказов с тестовыми данными.

Это **тормозит** систему, забивает индексы, делает прогон тестов медленнее (запрос «дай мне всех `user`s» теперь возвращает 80 000 записей вместо реальных 50).

Один раз в полгода кто-то «чистит вручную» — и всё повторяется.

#### Что становится с `seededAssetRepo`

После каждого прогона CI — **БД чистая**. Все созданные тесты сущности удалены. Никакого мусора. Никаких ручных чисток.

#### Где живёт в проекте

Папка `setup/` или `support/cleanup/`, файлы `seededAssetRepo.ts` (реестр) и `seededAssetReporter.ts` (reporter Playwright, который вызывает cleanup в `onEnd`).

#### Тонкий момент

`seededAssetRepo` работает **между процессами**. Reporter живёт в main-процессе Playwright, тесты — в worker-процессах. Чтобы реестр выживал между ними, он обычно **пишет в файл** (JSONL) и **читает** оттуда. Это сложнее, чем хранить в памяти, но критично для надёжности при hard-crash воркеров.

### Модуль 5. `withContext` / `TestError` — обогащение ошибок контекстом

#### Что делает

Это обёртка над `expect()`, которая **добавляет контекст** к каждой assertion. Если тест упадёт — в сообщении об ошибке будет указано: **какая сущность** (entity), **какое поле** (field), **какая бизнес-правило** (rule), **какие debug-данные** (debug fields).

```typescript
const check = withContext({
  entity: { type: 'Order', id: order.id, name: 'Test order' },
  section: 'Status field',
  query: 'createOrder',
});

check(response.data.createOrder.status, 'status')
  .rule('Order created with status=PENDING must persist that value')
  .toBe('PENDING');
```

#### Боль, которую решает

Без `withContext` — обычный `expect()`. Когда тест падает в CI, ты видишь:

```
Error: expect(received).toBe(expected)
Expected: "PENDING"
Received: "DRAFT"
```

И **всё**. Какая сущность? Какой ID? В каком тесте? Какое правило проверялось? Сидишь, ищешь.

С `withContext`:

```
Error: Order created with status=PENDING must persist that value
Entity: Order id=42 name="Test order"
Section: Status field
Query: createOrder
Expected: "PENDING"
Received: "DRAFT"
```

Сразу видно **что**, **где**, **почему** ожидалось. Дебаг — в разы быстрее.

#### Где живёт в проекте

Файл `support/assertContext.ts` или `support/testError.ts`. Кастомный класс ошибки (`TestError` или подобное) + factory-функция `withContext`.

#### Тонкий момент

`withContext` — это не замена `expect()`, а **дополнение**. Простые проверки (`expect(response.errors).toBeUndefined()`) остаются как есть. `withContext` применяется там, где **бизнес-смысл** ассертии важен и его надо записать.

### Модуль 6. `TestFailureReport` — структурированный отчёт о падении

#### Что делает

Это **builder**, который собирает полную картину падения теста: entity, шаг, GraphQL-запрос для воспроизведения, UI-путь для воспроизведения, DB-запрос для проверки, expected vs actual. На выходе — единый текстовый блок, готовый к копированию в Slack / Jira.

```typescript
const report = TestFailureReport.for('ORDER LIFECYCLE: confirmation rejected')
  .entity({ type: 'Order', id: order.id })
  .section('Phase', 'confirmation after payment')
  .graphqlRepro('UpdateOrderStatus', { id: order.id, status: 'CONFIRMED' })
  .uiRepro(`/orders/${order.id}`, ['Click Confirm'])
  .assertion({ field: 'status', actual: 'PENDING', expected: 'CONFIRMED' })
  .build();

expect(actualStatus, report).toBe('RELEASED');
```

#### Боль, которую решает

Без отчёта — упал тест, ты пишешь в Slack: «упал тест Х, скрин прикрепил». Команда задаёт **пять** уточняющих вопросов: «какой entity ID? на каком шаге? с какой попытки? какой запрос? какой ожидали ответ?». Полчаса переписки.

С отчётом — копируешь готовый блок, вставляешь, получаешь готовый ответ или Jira-тикет за пять минут.

#### Где живёт в проекте

Папка `support/reporting/`, файл `TestFailureReport.ts`.

#### Тонкий момент

`TestFailureReport` обычно применяется **только** в сложных integration-тестах, где падение требует контекста из нескольких источников. В простых API-тестах хватает `withContext` или плейн `expect()`.

### Подведём итог Части 2

Шесть модулей — шесть разных «приспособлений» на полке профессиональной мастерской:

| Модуль | Что закрывает |
| --- | --- |
| **`ConfigurationManager`** | Хаос `process.env`, опечатки, type assertions |
| **`AppPage` / `BasePage`** | Разрозненное логирование, неясные падения, разные стили POM |
| **`GraphQLClient`** | Копипаст HTTP-обвязки в сотне тестов |
| **`seededAssetRepo`** | Засор БД тестовыми сущностями после крашнутых тестов |
| **`withContext`** | «Expected true, got false» без объяснений |
| **`TestFailureReport`** | «Расскажи подробнее» в Slack после каждого падения |

Каждый — на своём слое. Каждый — написан **внутри** команды. Каждый — отвечает на конкретную боль, которая иначе вырастает на масштабе.

## Часть 3. Пример кода — один тест, три кастомных модуля

Возьмём небольшой тест. В нём задействованы **`ConfigurationManager`** (косвенно, через `apiClient`), **`GraphQLClient`** (создаём сущность через API), **`seededAssetRepo`** (регистрируем для cleanup), **`AppPage`** (UI-действия с автологированием).

### Код «с кастомным слоем»

Файл: `spec/orders/create-and-cancel.spec.ts`

```typescript
import { test, expect } from '../support/base';
import { seededAssetRepo } from '../setup/seededAssetRepo';

test('[C123] cancel order from list view', async ({ apiClient, ordersPage }) => {
  const created = await apiClient.createOrder({ status: 'PENDING' });

  seededAssetRepo.register({
    type: 'Order',
    id: created.id,
    label: created.id,
    deleteFn: (oid) => apiClient.deleteOrder(oid),
  });

  await ordersPage.navigate();
  await ordersPage.openOrderById(created.id);
  await ordersPage.clickCancelBtn();
  await ordersPage.confirmCancellation();

  const updated = await apiClient.getOrder(created.id);
  expect(updated.status).toBe('CANCELLED');

  await apiClient.deleteOrder(created.id);
  seededAssetRepo.unregister('Order', created.id);
});
```

### Разбираем построчно

#### Строки 1–2. Импорты

```typescript
import { test, expect } from '../support/base';
import { seededAssetRepo } from '../setup/seededAssetRepo';
```

- **`../support/base`** — кастомный `test` от Playwright. Внутри расширен фикстурами: `apiClient`, `ordersPage` и т.д. Это **`test.extend`** от Playwright, обёрнутый командой.
- **`seededAssetRepo`** — наш реестр созданных сущностей. Импортируется напрямую.

Заметь: **никакого** `process.env`. Никакого `axios`. Никакого `console.log`. Это работа **кастомного слоя**.

#### Строка 4. Сигнатура теста

```typescript
test('[C123] cancel order from list view', async ({ apiClient, ordersPage }) => {
```

- **`{ apiClient, ordersPage }`** — фикстуры, которые приходят из кастомного `base`. Каждая инстанс-фикстура **создаётся для теста** и **разрушается** после.
- **`apiClient`** — это инстанс `GraphQLClient`. Внутри уже использован `configManager.getBaseUrl()`, headers подложены, retry настроен.
- **`ordersPage`** — это инстанс Page Object'а, экстендящий `AppPage`. У него уже есть все action-обёртки с автологированием.

#### Строка 5. Создание сущности через API

```typescript
const created = await apiClient.createOrder({ status: 'PENDING' });
```

Одна строка. Внутри `createOrder`:
- Сформирована GraphQL-mutation.
- Подложены headers (auth, organization-id).
- Сделан запрос.
- Если 5xx — повторено до трёх раз.
- Ответ распарсен и валидирован по схеме.
- Возвращён типизированный объект `Order`.

**Без `GraphQLClient`** — это **двадцать строк** ручной обвязки. С — **одна**.

#### Строки 7–12. Регистрация в safety-net

```typescript
seededAssetRepo.register({
  type: 'Order',
  id: created.id,
  label: created.id,
  deleteFn: (oid) => apiClient.deleteOrder(oid),
});
```

Сразу **после** создания регистрируем сущность в реестре. Если тест дальше упадёт — reporter в конце прогона позовёт `deleteFn(created.id)` и удалит. БД останется чистой.

**Без `seededAssetRepo`** — если тест упадёт между этой точкой и финальным `delete`, сущность **останется** в БД. Через полгода — мусор.

#### Строки 14–17. UI-действия через Page Object

```typescript
await ordersPage.navigate();
await ordersPage.openOrderById(created.id);
await ordersPage.clickCancelBtn();
await ordersPage.confirmCancellation();
```

Четыре действия. Внутри **каждого** — `AppPage.click()` или `AppPage.fill()`. **Автоматически** логируется:

```
🧭 [OrdersPage] Navigating to /orders
🔍 [OrdersPage] Searching for order id=42
🖱️ [OrdersPage] Clicked "Order row #42" (38ms)
🖱️ [OrdersPage] Clicked "Cancel button" (52ms)
🖱️ [OrdersPage] Clicked "Confirm cancellation" (61ms)
```

Если на третьем шаге упало — в CI **сразу видно**, **где** именно. Не нужно угадывать.

**Без `AppPage`** — пришлось бы либо писать `await page.locator('...').click()` без логов, либо добавлять `console.log` к каждому действию руками.

#### Строки 19–20. Финальная проверка через API

```typescript
const updated = await apiClient.getOrder(created.id);
expect(updated.status).toBe('CANCELLED');
```

После UI-действий — **спросили API**, что статус действительно сменился. Это **более надёжно**, чем проверять через UI (UI может отрисовать одно, а в БД — другое; API-ответ всегда отражает реальное состояние).

#### Строки 22–23. Cleanup (happy path)

```typescript
await apiClient.deleteOrder(created.id);
seededAssetRepo.unregister('Order', created.id);
```

Если дошли сюда — тест **прошёл успешно**. Удаляем сущность сами и снимаем регистрацию (чтобы reporter не пытался удалить второй раз).

### А теперь — как этот тест выглядел бы БЕЗ кастомных модулей

```typescript
import { test, expect } from '@playwright/test';
import axios from 'axios';

test('cancel order from list view', async ({ page }) => {
  const apiUrl = process.env.API_URL ?? 'http://localhost:3000/graphql';
  const token = process.env.API_TOKEN;
  const orgId = process.env.ORG_ID;

  const createResponse = await axios.post(apiUrl, {
    query: `mutation { createOrder(input: { status: "PENDING" }) { id status } }`,
  }, {
    headers: {
      'Authorization': `Bearer ${token}`,
      'X-Organization-Id': orgId,
      'Content-Type': 'application/json',
    },
  });

  const orderId = createResponse.data.data.createOrder.id;
  console.log('Created order: ' + orderId);

  await page.goto(process.env.BASE_URL + '/orders');
  // ... ещё ~30 строк ...
});
```

**Сравни:**
- Версия с кастомом — **~23 строки**.
- Версия без кастома — **~45 строк**, и в ней **трёхкратный копипаст** auth-блока.

А если в проекте таких тестов **сто**? Это **четыре с половиной тысячи** строк копипаста. И **любое** изменение auth-схемы — в **ста** местах.

### Главное, что нужно унести из примера

Кастомный слой **не делает тесты сложнее**. Он делает их **короче, читаемее, надёжнее**. Цена — один раз написать модуль. Выгода — каждый тест в проекте.

И это работает **только при масштабе**. На двух тестах разница не видна. На двухстах — кастомный слой экономит **дни** работы.

## Часть 4. Когда команда начинает писать кастомные модули

Кастомные модули **не появляются сразу**. Это **эволюция**, и она типична для всех команд, которые прошли путь от десяти тестов к тысяче.

<Diagram id="evolution-of-custom-modules" caption="Кастомные модули — это **эволюция, а не план**. Команда дорастает до них через боль." />

### Этап 1. Один тест — голый Playwright

```typescript
test('login works', async ({ page }) => {
  await page.goto('http://localhost:3000/login');
  await page.fill('[name=email]', 'test@example.com');
  await page.fill('[name=password]', 'pass');
  await page.click('button[type=submit]');
  await expect(page.locator('h1')).toContainText('Welcome');
});
```

Идеально. Чисто. Никаких кастомных модулей не нужно — добавляет шум.

**Никаких** модулей. Голый Playwright. На один тест — нормально.

### Этап 2. Десять тестов — первый helper

Десять разных тестов начинаются с одного и того же логина. Появляется **первый кастомный** код:

```typescript
async function login(page, email, password) {
  await page.goto('http://localhost:3000/login');
  await page.fill('[name=email]', email);
  await page.fill('[name=password]', password);
  await page.click('button[type=submit]');
}
```

Это **зародыш** кастомного слоя. Маленькая функция. Не модуль ещё. Но **первый шаг**.

### Этап 3. Пятьдесят тестов — первый Page Object

К десяти добавляется пятнадцать тестов про карточку юзера, десять — про список, пять — про настройки. Помимо логина появляются **повторяющиеся действия** в других местах.

Команда понимает: helpers — это **плоско**. Нужна **структура**. Появляется **первый Page Object**:

```typescript
class LoginPage {
  constructor(private page: Page) {}

  async navigate() { await this.page.goto('/login'); }
  async fillEmail(email: string) { await this.page.fill('[name=email]', email); }
  async fillPassword(pwd: string) { await this.page.fill('[name=password]', pwd); }
  async submit() { await this.page.click('button[type=submit]'); }
}
```

Это **уже** слой. Не «модуль» в полном смысле — но **архитектурное решение**: «каждой странице — свой класс».

### Этап 4. Двести тестов — `ConfigurationManager` рождается

В двадцати тестах появилось `process.env.BASE_URL`. В пятнадцати — `process.env.API_TOKEN`. Кто-то опечатался: `BASE_URL` vs `BASEURL`. Тест упал в CI без понятной ошибки.

Команда садится и говорит: «хватит. Все настройки — через один объект».

Так рождается **`ConfigurationManager`**. Не из «красивости» — из **боли**. Из конкретного incident'а, когда полдня искали опечатку.

### Этап 5. Пятьсот тестов — `GraphQLClient` рождается

Половина тестов делает `axios.post(...)` к API. В каждом — headers, auth, error-handling. Когда меняется auth-схема, надо обновить **в ста местах**.

Кто-то говорит: «давайте сделаем один клиент». Через две недели появляется **`GraphQLClient`**. Все API-вызовы переезжают в него. Сотня тестов становится короче на пять строк каждый.

### Этап 6. Тысяча тестов — `seededAssetRepo` рождается

В staging-БД 30 000 «Test QA: User 1718...». Прогон тестов идёт **в полтора раза дольше**, потому что запрос «дай user'ов» возвращает огромный список. Никто не помнит, какие из этих 30 000 — реальные, а какие — мусор.

Команда садится и решает: «каждый тест **обязан** удалить за собой. И для надёжности — реестр + cleanup-reporter».

Так рождается **`seededAssetRepo`**. Через месяц — БД чистая. Прогоны быстрее. Все счастливы.

### Этап 7. Несколько тысяч тестов — `withContext` и `TestFailureReport`

К тысячам тестов добавляются **integration** и **lifecycle**-сценарии — где один тест проходит через десять шагов на разных страницах. Когда такой тест падает, разобраться **невозможно** — стек-трейс показывает один кадр, а тест уже на восьмом шаге.

Команда пишет **обёртку** для assertions, которая добавляет контекст. И **builder** для отчёта о падении, который пишет полную картину в Slack.

Так появляются **`withContext`** и **`TestFailureReport`**. На этом этапе команда — уже **профессиональная мастерская**.

### Главная мысль про эволюцию

Никто не пишет шесть модулей **сразу**. Это **постепенно**. На каждом этапе — **конкретная боль**, которая толкает к написанию **следующего** модуля. Без боли — модуль не появится, потому что **зачем**.

И если ты сегодня видишь проект, в котором есть **все шесть** — это значит, что команда прошла **полный путь**. Это **зрелый** проект. С его стеком можно прожить три-пять лет без боли роста.

Если видишь проект, в котором есть **два-три** — это проект **в середине пути**. Он перевалил за этап «один helper», но ещё не дошёл до полной зрелости. Это **типично**.

Если видишь проект, в котором **нет ни одного** — это либо очень молодой проект, либо «застрявший» в начальном этапе. Если в последнем — команда **скоро упрётся в стену**. Стоит начать писать кастом раньше, чем боль станет невыносимой.

## Часть 5. А зачем мне это знать как QA?

Пять причин, почему **знание кастомного слоя** меняет твою работу. Это самые «инженерные» причины из всего курса.

### Причина 1. Видишь, ЧТО твоё, что стандартное

Когда ты читаешь чужой код — ты сразу различаешь:

- `import { test, expect } from '@playwright/test'` — **стандартное**, из Playwright.
- `import { test, expect } from '../support/base'` — **кастомное**, обёртка команды.
- `import { faker } from '@faker-js/faker'` — **стандартное**, из npm.
- `import { userFactory } from '../support/factories/userFactory'` — **кастомное**, на основе Fishery+Faker.

Это даёт тебе **двойное** видение проекта. На любой код ты можешь сказать: «это из библиотеки, документация открывается за пять секунд» или «это написано **внутри** команды, надо открывать исходник».

Это **в разы** ускоряет работу с чужим кодом. Раньше ты тратил час на то, чтобы понять, **откуда** взялся какой-то `apiClient`. Теперь — открываешь импорт, видишь `../support/`, идёшь в исходник, читаешь.

### Причина 2. Оцениваешь зрелость проекта за пять минут

На onboarding в новую команду — открываешь репозиторий и смотришь:

- Есть ли в `support/` файл вроде `configManager.ts`? **Если да** — проект перешагнул через `process.env` хаос.
- Есть ли базовый `AppPage` или `BasePage`? **Если да** — POM-слой зрелый.
- Есть ли `graphqlClient.ts` или подобное? **Если да** — API-обвязка консолидирована.
- Есть ли реестр созданных сущностей? **Если да** — БД чистится автоматически.
- Есть ли обёртка над `expect` с контекстом? **Если да** — команда дошла до тонкого дебага.

За **пять минут** ты понимаешь, на каком этапе из семи находится проект. И уже знаешь, **чего ждать**. Если все шесть модулей — это зрелый проект, в нём ты сразу можешь писать продуктивные тесты. Если двух нет — на onboarding'е ты предложишь начать с них.

### Причина 3. Можешь предложить вынести что-то в кастомный модуль

Самая важная для **карьерного роста** причина.

Junior QA пишет тесты «как есть». Middle QA замечает дублирование. **Senior QA** видит дублирование и **предлагает решение** — конкретный модуль, который уберёт боль.

Пример. Команда жалуется: «у нас в десяти местах прописан `process.env.STAGING_URL`, и постоянно опечатки». Junior говорит «ну, надо аккуратнее». Senior говорит:

> «Давайте я заведу `ConfigurationManager` — singleton с типизированными геттерами. Я могу сделать MVP за день, потом постепенно мигрируем тесты».

Это **другой уровень разговора**. Это **инженерный** подход, не «галочный QA». И **за это платят больше**.

### Причина 4. На code review видишь рычаги

Ты читаешь PR коллеги. Видишь:

```typescript
const url = process.env.API_URL;
const response = await axios.post(url, { ... }, { headers: { ... } });
```

Раньше ты бы прошёл мимо — «ну работает же». Теперь — комментарий:

> «У нас есть `GraphQLClient` в `support/api/`, используй его — там auth и retry уже встроены».

Это **конструктивное** замечание. Не «можно переписать», а **«вот уже готовый инструмент**». Разработчик правит за минуту, PR становится лучше, проект — последовательнее.

### Причина 5. Понимаешь, почему «у нас всё нестандартно»

Когда ты приходишь в зрелый проект и видишь, что половина кода **не как в туториалах** — у тебя может возникнуть мысль «зачем они изобрели велосипед?».

Теперь — ты видишь не «велосипед», а **накопленную мудрость**. Каждый кастомный модуль — это **закрытая боль**, которая у команды была. Никто не пишет модуль ради красоты. Пишут, когда **больно стало**.

И ты можешь **спросить** коллег: «расскажите, как у вас появился `GraphQLClient`? Какая была боль?». Они с удовольствием расскажут — каждый модуль имеет свою историю. И ты быстро **встроишься** в команду, потому что **понимаешь** их инженерные решения.

## Часть 9. Глоссарий нового урока

<Glossary
  terms={[
    { term: 'Кастомный модуль', definition: 'Код, написанный **внутри** команды (не из npm), который дополняет стандартный стек.' },
    { term: 'Singleton', definition: 'Паттерн, при котором объект существует в проекте **в одном экземпляре**. Например, `configManager`.' },

### Несколько практических советов на старт

Если ты хочешь применить знания **сегодня же**:

1. **Открой `support/`** (или `spec/support/`) в своём проекте — посмотри, какие там файлы. Каждый — кандидат на кастомный модуль.
